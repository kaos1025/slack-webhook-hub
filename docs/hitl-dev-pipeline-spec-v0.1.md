> **출처**: P1-3-B 후속 Slack 통합 논의 (2026-06-05). 사람 개입(gate)이 있는 Slack 기반 원격 개발 파이프라인.
> **관계**: `SLACK-WEBHOOK-HUB`(인프라/전송 레이어) 위에서 도는 **워크플로우**. 실행 레이어는 폴링 routine(`trig_01F3b24fyHFpZJbHfHumuxwt`) 또는 웹훅 허브.
> **철학**: codex goal류 **완전 무인의 "프로젝트가 산으로 가는" 리스크**를, 2개 human gate(plan 승인 · PR 머지 승인)로 차단. 실행은 위임하되 **통제권은 사람이 쥔다.**
> **우선순위**: P2 (PoC 검증 후 점진 발전)

---

## 1. 목표 & 비목표

- **목표**: 실행(코딩)은 원격 위임, 방향·결과 **통제는 사람**. Slack = 통신 채널 + 모바일 가시성 + 작업 기록.
- **비목표**: 완전 무인 실행, 사람 검증 생략, gate 자동 통과.

## 2. 역할 — "두 클로드 + 사람"

| 역할 | 정체 | 책임 |
|---|---|---|
| **지휘자 (Conductor)** | 대화 세션 Claude | 프롬프트 공동작성 · Slack 송수신 · plan/PR 리뷰 보조 · `run-now` 트리거 |
| **실행자 (Executor)** | remote routine / Claude Code | 명령 수신 · plan 작성 · 구현 · PR 생성 |
| **운영자 (Operator)** | 사람 (kaos1025) | **최종 승인 gate**(plan, PR 머지) · 사용자 검증 |

## 3. 상태 머신 — thread 1개 = 작업 1건

실행자는 stateless(매 실행 독립)이므로 **Slack thread가 곧 상태 저장소**다.

```
SUBMITTED ─→ PLAN_REPORTED ─(gate1: 사람 승인)→ PLAN_APPROVED
   ─→ PR_OPENED ─(gate2: 사람 머지승인)→ MERGE_APPROVED ─→ MERGED
```

**실행자 판단 로직 (매 run마다 thread 읽고):**
- PLAN 없음 → plan 작성·보고 후 **멈춤**
- PLAN 있고 승인 없음 → **대기** (gate 1)
- PLAN_APPROVED & PR 없음 → 구현 + PR 생성·보고 후 **멈춤**
- PR 있고 머지승인 없음 → **대기** (gate 2)
- MERGE_APPROVED → 머지 → MERGED

## 4. 단계 마커 (thread 메시지 규약)

자연어 추론보다 **명시적 마커**로 단계를 판별(견고성):

| 마커 | 발신 | 의미 |
|---|---|---|
| `[작업] <명세>` | 지휘자/사람 | 파이프라인 시작 |
| `[PLAN] ...` | 실행자 | plan 보고 (gate1 대기) |
| `[승인]` | **사람만** | plan 승인 |
| `[PR] <링크> ...` | 실행자 | 구현 완료 + PR (gate2 대기) |
| `[머지]` | **사람만** | 머지 승인 |
| `[보류] <사유>` | 실행자 | 거부/확인 질문 |

## 5. 진행 트리거 — 폴링 우회 (핵심)

지휘자(세션)가 각 gate 통과 직후 **`RemoteTrigger run`으로 실행자를 즉시 깨운다**(초 단위):
- 프롬프트 outbound **+ run** → 즉시 plan
- `[승인]` 확인 **+ run** → 즉시 구현+PR

폴링(매시 정각)은 **지휘자 부재 시 백업**일 뿐. 평소엔 즉각 흐른다.

## 6. 발신자 신뢰 정책 (보안 핵심)

- 명령/프롬프트: 지휘자(봇 ID) 또는 운영자(사람) 허용
- **승인 gate(`[승인]`, `[머지]`): 운영자(사람)만** — 봇 승인 금지(이게 무인화 방지의 핵심 잠금)
- 그 외 발신자/봇/시스템 메시지: 무시
- 화이트리스트 = `Operator user_id` + `Conductor 봇 ID` (명시적 등록). 단 gate는 Operator로만 잠금.

## 7. PR 흐름

- 실행자: `feat/...` 브랜치 → 구현 → conventional commit → **push → PR**(squash 예정, no-auto-merge) → thread에 `[PR] 링크`
- **선결**: 실행자 환경의 **GitHub push 인증**(토큰/deploy key). 미설정 시 작업물 소실(persist_session=false).
- 머지: gate2 승인 후 실행자 또는 지휘자가 squash 머지.

## 8. 사용자 검증 지점

- **gate1(plan)**: 접근 방향 검증
- **gate2(PR)**: 코드 검증
- **추가 수동 검증**(QA, 브라우저, 결제 플로우 등): 운영자가 직접 수행 후 thread에 결과 기록 → 이후 단계 진행

## 9. Phase / 난제

| Phase | 내용 |
|---|---|
| **0** | 선결 검증 — GitHub push 인증 + 지휘자 봇 발신 ID 확정 + routine 외부 발사(웹훅 시) |
| **1** | 단일 작업 e2e: 프롬프트→plan→승인→PR→머지 |
| **2** | 마커 규약 + thread 멱등 + gate 멈춤 견고화 |
| **3** | 멀티 작업(thread 병렬) + 멀티 프로젝트(채널별) |

**난제**: 동시 작업 충돌(브랜치/thread 격리), 긴 작업의 세션 시간 한계, 마커 누락 시 fallback, 머지 후 후속 검증 루프.

## 10. 발전 경로 (MCP / 플러그인)

PoC(현 routine + 수동 지휘) → 반복 패턴 확립 → **플러그인**(스킬/커맨드/훅 번들) → **MCP**(도구 표준화) → 배포. 단 **YAGNI**: 추출은 PoC로 가치 검증 후. (§별도 논의)
